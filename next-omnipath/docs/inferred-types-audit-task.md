# Task: Audit custom result/types vs inferred Drizzle types

## Goal
Review the Next.js app and identify where we still use custom TypeScript types even though we could use types inferred from the Postgres/Drizzle schema or from the actual query result shapes.

Main question:
- Can the frontend work directly with the shapes returned by the new Postgres/Drizzle-backed queries and tables, instead of maintaining compatibility-era custom types?

## Context
We previously had Meilisearch-oriented result types and compatibility fields like `_formatted`.
We are now on Postgres + Drizzle.
Some cleanup has already happened:
- `_formatted` usage has been removed
- entity-specific typing has started to move toward inferred Drizzle types
- but there are still custom UI/result types that may no longer be necessary

## What to audit
Focus on these areas first:

- `src/types/entities.ts`
- `src/types/search-results.ts`
- `src/types/search.ts`
- `src/lib/postgres-search/search.ts`
- `src/lib/queries.ts`
- `src/features/search/components/result-card.tsx`
- `src/features/search/components/entity-details-dialog.tsx`
- `src/features/search/page.tsx`
- `src/features/explore/components/entities-explore-tab.tsx`
- any other files importing custom result types from `src/types/*`

Also inspect Drizzle-derived types available from:
- `@next-omnipath/drizzle`
- generated schema in `drizzle/schema.ts`

## Deliverables
Please produce:

1. A short inventory of places where we use:
   - fully custom types
   - partially custom view-model types
   - inferred Drizzle types

2. For each custom type, classify it as one of:
   - **necessary**: true frontend view-model / computed shape / aggregated result
   - **replaceable**: can be replaced by inferred Drizzle type directly
   - **should be query-local**: not a shared type, should live next to the query that produces it

3. A concrete migration plan with low-risk steps.

## What to look for
Flag places where we:
- duplicate table row fields manually
- rename fields only for legacy reasons
- maintain broad “catch-all” result types for mixed result kinds
- cast through `unknown` because the real query/result type is missing
- use shared global types where a query-local result type would be better
- can use `InferSelectModel<typeof table>` or `table.$inferSelect`
- can derive frontend props from the actual server/query return type instead of hand-written interfaces

## Preferred direction
In general, prefer:

1. **Drizzle inferred types** for real table rows
2. **small explicit query result types** for joins/aggregates/projections
3. **narrow UI prop types** close to the component using them
4. avoid one giant shared result type spanning entities, CV terms, sources, legacy search, etc.

## Non-goals
- Do **not** edit `drizzle/schema.ts` manually; it is autogenerated.
- Do not force Drizzle row types onto places that are clearly computed/aggregated view models.
- Do not preserve old Meilisearch compatibility shapes unless there is a real current need.

## Output format
Please add your findings as a short markdown note with:
- summary
- inventory table
- recommended changes
- suggested order of implementation
